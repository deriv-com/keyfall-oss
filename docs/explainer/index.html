How to connect your agents to an MCP server, signing in with your company SSO

Alex wants Claude Code to use My App

Alex wants Claude Code, an AI agent, to read data from My App.

The usual way: paste an API key into Claude Code's config.

Keys get copied, and every copy works forever.

Our way: one URL, two steps

The config holds only a URL. Nothing secret.

Alex adds the server, then clicks Allow. That's all Alex ever does.

Behind the scenes: four players

On Alex's laptop: Alex's browser, and Claude Code, the AI agent.

On our side: the MCP server with the data, and the Allow page behind your SSO.

Why is the Allow page separate?

If SSO guarded the whole server, the browser could log in, but Claude Code would get stuck.

So split it: the MCP server stays public and checks tokens. Only the Allow page is behind SSO.

They trust each other through one shared signing key: one signs, the other checks.

What happens after Alex adds the server

Claude Code asks for data, without a token.

The server says no, and tells Claude Code where to sign in.

Claude Code reads the sign-in details and registers itself. It gets an ID (client_id).

Claude Code makes a random secret and its hash. It keeps the secret to itself.

Claude Code opens a browser tab on Alex's laptop.

The tab carries the hash of Claude Code's secret, never the secret itself.

The server sends the browser to the Allow page, with a signed note.

SSO checks it's really Alex. Outsiders stop here.

The page asks Alex. Alex clicks Allow.

The Allow page signs a 60-second code and sends the browser to localhost with it.

The browser hands the code to Claude Code, which is listening on localhost.

Claude Code sends the one-time code and the secret, straight to the server over HTTPS.

The server hashes the secret. It matches, so Claude Code gets an access token (1 hour) and a refresh token.

Every request now carries the token.

Two steps for Alex. Everything else happens on its own.

How the code gets back to Claude Code

Alex's browser can log in with SSO. Claude Code is an AI agent, not a browser, so it can't.

So Claude Code opens a tiny listener on Alex's own laptop.

After Allow, the browser is sent to that address with the code. Claude Code is listening, so it gets it.

PKCE: proving Claude Code is the one who asked

The code travels inside a URL. URLs end up in history and logs, and another app could grab them.

Agents have no password of their own, so without PKCE, whoever has the code gets the token.

With PKCE, Claude Code made a secret at the start and keeps it in memory. Only its hash goes into URLs.

Claude Code reveals the secret once, straight to the server over HTTPS. The thief only ever saw URLs.

Why can't you reverse the hash?

SHA-256 is a hash, not encryption. There is no key, so there is nothing to decrypt.

Change one character and the whole hash changes. There are no clues to follow back.

The only attack is guessing, and it would never finish.

Every credential has a timer

The signed note gives Alex 10 minutes to sign in and click Allow.

The code only has to make one hop, so it lives 60 seconds and works once.

Claude Code attaches the access token to every request. If it leaks, it's dead within the hour.

Each refresh swaps the refresh token for a new one. The chain ends 14 days after the Allow.

An admin can revoke Alex at any time, and every one of them stops working.

The Allow page is the front door

The one page Alex sees: who, which role, and where the code goes.

If it can't check something, there is no Allow button.
